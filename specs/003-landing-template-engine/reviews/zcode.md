## Summary

The artifact set is unusually disciplined — risk-scored RTM, ISO 29119 test cases, honest pre-mortem — and the codebase claims it makes are mostly verifiable (the `isUnderundre` couplings, static legal-link spans, and the TCO-specific lead enum all exist as described). The headline weakness: the spec refactors the **API contract and the content layer without covering their existing consumers**. The one live lead-capture form posts a payload the new schema rejects, and there is no task to migrate it; the bilingual content requirement collides with monolingual JSON schemas; and `/manifest` is asserted as a static route for a brand that will have no manifest data. All three are cheap to fix on paper, but as written they ship regressions the planned QA suite cannot catch (every lead test drives the API via curl, never through the real form).

## Alternative approaches considered (lens G)

- **Registry mutation vs auto-discovery** for scaffolded brands (F9): fs-scan of `projects/` removes a codegen step and a failure mode; worth a deliberate decision, not a default.
- **Client-side lang toggle vs statically rendered bilingual legal pages**: current i18n is a client context; for statutory pages, statically rendering both languages (or per-locale routes) would make legal text crawlable/archivable and keep the pages truly `○ (Static)` with content in the HTML. Worth weighing for `/privacy` and `/terms` specifically — legal text that only exists after hydration is an odd look for a compliance page.
- **locales.ts → JSON extraction direction**: instead of hand-maintaining bilingual JSON, generate `data/*.json` from `locales.ts` once (script) so the migration can't silently drop the RU blocks. Complements F2's fix.
